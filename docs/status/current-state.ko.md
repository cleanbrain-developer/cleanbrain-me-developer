- **Toolchain note**: `vitest@5`와 그것이 끌어오는 `vite`/`rolldown`은 Node의 `node:util` `styleText` export(Node ≥21.7/22)를 요구하는데, 이 환경의 Node 20.11.1에는 이것이 없다 — 이를 시도하면 단순한 `engines` 경고가 아니라 startup 시점에 `SyntaxError`로 실패한다. 대신 `vitest@^3.2.7`을 고정했다(내부적으로 `vite` 5.x, Node `20.x` 완전히 지원됨); `npm audit`은 `vitest@5`로만 고쳐지는 2개의 moderate `@vitest/mocker` advisory를 보고한다(vitest 자체의 local mock-transform server에 있는 dev-only path-traversal/arbitrary-file-read 위험으로, 빌드된 Next.js 앱에는 존재하지 않으며 CI의 non-interactive `vitest run`에서도 도달할 수 없다). 이 환경(또는 CI)이 Node ≥22를 실행하게 되면 vitest 버전 고정을 재검토할 것. (`vitest@5`에 대한 중간 시도는 관련 없는 npm 10.2.4 arborist 버그를 우회하기 위해 잠시 `npm install --legacy-peer-deps`가 필요했다 — 버전이 `^3.2.7`로 고정된 지금은 그 우회책이 필요 없으며, 일반 `npm install`/`npm ci`가 동작한다. 둘 다 아래 "Deployment prep"에서 검증되었다.)

## Known constraints

- V1에는 backend, database, authentication, CMS가 없다(`docs/product/scope.md` 참고).
- 이 사이트에는 이제 mock/simulation UI가 없다(ADR-0005) — 그 질문을 명시적으로 다시 여는 새로운 ADR 없이는 합성 "이벤트 생성" 기능을 재도입하지 않는다. `relayhub-java` 통합은 `GET`-only이며 이미 public한 endpoint로 CORS 범위가 한정되어야 한다; 방문자로부터의 임의의 URL, header, script, credential 입력은 절대 구현되어서는 안 된다(`.specify/memory/constitution.md` 참고).
- 대상 cluster는 2 vCPU / 4 GB RAM / 40 GB disk이다(`cleanbrain-me-infra` 기준) — 모든 서비스에 걸친 결합 resource budget이 이미 이 상한선에 근접하고 있으므로(해당 repository의 README와 `cleanbrain-me-entrance` 자체의 `current-state.md` 참고), 이 앱은 가벼운 상태를 유지해야 한다.
- 이 repository는 애플리케이션 source, Dockerfile, CI를 소유하고, `cleanbrain-me-infra`는 production Kubernetes manifest를 소유한다 — 둘은 서로의 콘텐츠를 중복해서는 안 된다. 필요한 infra 변경으로 보이는 것은 여기서 구현하지 않고 `docs/infra-required-changes.md`에 기록한다.
- maintainer의 명시적인 선택에 따라, 사이트 어디에도 real한 시간순 근무 이력 timeline(회사 이름, 직함, 날짜)이 없다 — Experience/Resume은 오직 focus-area narrative일 뿐이다. maintainer가 나중에 명시적으로 timeline을 요청하는 경우에만 재검토한다.
- 케이스 스터디는 의도적으로 composite/추상화되어 있으며 real한 metric이 없다 — maintainer가 명시적으로 real하고 공개 가능한 숫자를 제공하지 않는 한 나중에 숫자를 "채워 넣지" 않는다.
- 이 애플리케이션은 server runtime이 없는 static export다(ADR-0003) — 진짜 server-side logic(API route, middleware, request당 server rendering)이 필요한 향후 feature는 단순히 feature를 추가하기 전에 먼저 그 ADR을 재검토해야 한다.
